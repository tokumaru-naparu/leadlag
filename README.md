# LeadLag Strategy

## 何を作ったか

米国セクターETFの値動きから日本業種ETFの翌日リターンを予測する統計的アービトラージ戦略。

## なぜ作ったか

金融論文（PCA with Subspace Regularization）の手法を実装し、実データで検証したかった。
バックテストだけでなく、GitHub Actionsで日次データ更新・シグナル計算・レポート配信を完全自動化することで、実運用可能な基盤を構築した。
理論と実装の両面から定量戦略の開発プロセスを理解することが目的。

## 動いている機能

- **論文ベースのPCA SUB実装**: λ=0.9, K=3の部分空間正則化PCAによるシグナル生成
- **フル期間バックテスト**: 2010年から16年分のデータで戦略パフォーマンスを検証
- **IC相関テスト**: 候補銘柄を期間分割してシグナルの安定性を統計的に評価
- **ETF版 vs 個別株版の比較分析**: 流動性・コスト・リターンの3軸で実装可能性を判定
- **GitHub Actionsによる完全自動化**:
  - 平日07:00 JSTに自動実行（cron）
  - yfinanceでデータ取得 → PCA計算 → CSV更新 → git push
  - 日次レポート生成・SMTP経由でメール配信
- **17業種のシグナルランキング**: ロング上位3業種・ショート下位3業種を選定
- **ドローダウン制御**: DD水準に応じてポジションサイズを動的調整

## 動いていない機能と理由

- **メール配信機能**: GitHub SecretsにSMTP認証情報（SMTP_HOST/USER/PASS）が未設定のため送信失敗
- **個別株版の実運用**: Phase3の比較分析でETF版よりSharpe・DDが劣る結果となり、流動性リスクも高いため採用見送り

## 使用技術

- **言語**: Python 3.11
- **データ処理**: pandas, numpy
- **データ取得**: yfinance（米国・日本ETF）
- **統計処理**: 固有値分解（numpy.linalg.eigh）、相関係数計算
- **CI/CD**: GitHub Actions（スケジュール実行、自動コミット）
- **通知**: smtplib（メール送信）
- **その他**: jpholiday（営業日判定）

## 詰まったこと・学んだこと

**論文実装の難しさ**
- 論文の数式をそのままコード化すると計算誤差や次元不一致でエラー。行列の転置・正規化の順序を何度も見直した。
- Cfullの推定期間（2010-2014）が固定パラメータとして重要だが、論文に明記されておらず試行錯誤が必要だった。

**バックテストの罠**
- 短期間（2021〜）のデータでIC相関テストを行い、良好な結果が出たが、フル期間（2010〜）で再検証すると有意性が消失。サンプルサイズの重要性を痛感。
- シグナルのshift処理を間違えると未来のデータを使ったルックアヘッドバイアスが発生。date indexの扱いに細心の注意を払った。

**GitHub Actionsでの自動化**
- cronの時刻がUTC基準で、日本時間との変換ミスで実行タイミングがずれた（22:00 UTC = 翌07:00 JST）。
- yfinanceのデータ更新タイミングが不定期で、米国市場引け後すぐだとデータが取得できないケースがあった。
- git pushの権限設定（GITHUB_TOKEN）とコミット時のユーザー設定を理解するのに時間がかかった。

**統計的評価の重要性**
- Phase1のIC相関テストで期間分割（2010-2015 / 2016-2020 / 2021-）を行い、全期間でプラスの業種だけを採用する判定ルールを実装。単一期間の結果だけでは過学習リスクが高い。
- ETF版（Sharpe 2.04）と個別株版（Sharpe 0.88）で明確な差が出たことで、流動性・スプレッドコストが戦略パフォーマンスに直結することを実感。

**データパイプラインの設計**
- 既存CSVへの追記処理（append mode）で、カラム順序の不一致や重複行の混入に悩んだ。最終的にstate管理とカラムオーダー保持の仕組みを実装。
- performance.csvの累積資本計算で、初期値（1,000,000円）との整合性を保つロジックを慎重に設計した。
